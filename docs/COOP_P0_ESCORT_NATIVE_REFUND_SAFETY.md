# P0 Native Escort Escrow — proof-gated atomic refund

Draft safety infrastructure only, default OFF. This branch extends the native wallet provider, not the trusted NPC failure producer or live player-facing contract engine. It may NOT be deployed as full refund gameplay without additional verified native failure evidence.

## How it works

- Existing PR #69 source (already present on main) reserves real NPC corporation cash division in GameStore SQLite and settles exactly two player balances with a single transaction.
- New refundAtomic(contract) is a terminal alternative to settleAtomic. It refuses to run unless EVEJS_COOP_ESCORT_REFUNDS=1 AND its creator was injected with a server-side verifyNativeFailure callback.
- verifyNativeFailure must return durable, irreversible, authoritative proof of an actual native hauler wreck or an explicitly canceled route that had never issued warp; mere timeouts, missing ship objects, lost ACK, or user-requested strings are not valid evidence.
- The witness must exactly match the immutable contract, manifest, NPC corporation, failureWitnessID, nativeDurable, deliveryImpossible and noPriorPayout.
- Under the SAME existing GameStore atomic transaction, refundAtomic reads the original RESERVED escrow, adds exactly the previously deducted ISK back to the native corporate wallet and journal, and marks that escrow REFUNDED with failure witness ID. Any SQL failure rolls all of this back.
- Existing settleAtomic insists on RESERVED and therefore cannot pay a REFUNDED contract; refundAtomic also insists on RESERVED and cannot refund a SETTLED one. A repeat refund is rejected.
- verifyRefund reads the durable authoritative escrow row and exact original contract. It is safe after server restart; it NEVER recredits money.
- No separate synthetic wallet, faucet, compensation mint, client RPC or autogenerated refund after timeout.

## Stage A contract-journal integration (second P0 slice)

The branch also modifies integration/coopEscortContractSettlement.cjs and its native contract test suite.

- Original accepted journal sequence OFFERED -> FUNDING_PREPARED -> FUNDED -> SETTLEMENT_PREPARED -> SETTLED is preserved.
- A separate terminal branch is now accepted only from FUNDED: REFUND_PREPARED -> REFUNDED. Both mutually exclusive paths are immutable in the same journal format.
- refund(contractID) first checks the server-side native failure source, the independently verified native payout/refund status, and the terminal native delivery status. A delivered route, unknown delivery, missing authority or unsupported native wallet is NOT refundable.
- A fsynced REFUND_PREPARED event is written before invoking the atomic corporate refund, and a native verifyRefund receipt with matching contract, amount and real wreck witness is independently required before appending REFUNDED.
- An uncertain refund leaves the writer lock and journal pending. inspectRefundRecovery() only REPORTS whether the durable native money refund exists: it NEVER repeats credits, removes the writer lock, or fabricates a successful terminal.
- Stage A proof() now returns the REAL pirate nativeWreckID after full warehouse, combat and two-pilot verification. Read-only post-settlement proof can verify the terminal dual-wallet receipt in place of still-RESERVED escrow; this allows a later audited reputation entry without authorizing another payment.

Five additional contract refund Node test scenarios were committed. In this session 9/9 isolated V8 tests verified actual committed Stage A source through an injected in-memory filesystem: accepted real offer, one corporate reserve, no loss no refund, delivered plus loss conflict blocks, uncertain result remains REFUND_PREPARED and lock remains, manual inspection does not retry. This is NOT evidence of real pinned better-sqlite3 or EVE client gameplay.

**Important:** the native failure reader and the wallet provider's independent verifyNativeFailure are not wired to real EVE object/wreck provenance. This feature remains OFF; do not treat a mocked witness as accepted live refund proof. Full paid Escort gameplay issue #82 is open.


## P0 unified runtime coordinator (third slice)

integration/coopEscortRuntime.cjs now composes the previously independent Stage A contract ledger, Stage B native ISK wallet, Stage C pre-warp flight gate and post-raid proof. The reversible overlay installer explicitly registers all four modules. Runtime creation demands an already-authorized in-process GameStore SQLite atomicRows provider, true NPC corporation predicate, independent native duo verifier, manifest/warehouse/incident/outcome sources, actual operator offer authority and real terminal failure authority; it DOES NOT discover or fake those sources.

The trusted booking path verifies both genuine native player IDs and their actual fleet before the first NPC corporate reserve. finishAfterRaid() creates and attaches the real post-raid Stage A contract to the SAME pre-warp escrow and independently proves physical delivery, two real player hits/wreck and warehouse custody before consuming escrow in one two-wallet SQL commit. Duplicate settlement is rejected.

The cross-stack integration exposed a **real defect fixed here**: on an existing RESERVED escrow, native verifySettlement returns NOT_SETTLED (not NOT_FOUND), and verifyRefund returns NOT_REFUNDED. Stage A previously rejected both as non-empty preflight even though they are exactly the unpaid/unrefunded states. The new preflight accepts these negative terminal observations ONLY after independently verifying the original reserved receipt, while rejecting SETTLED/REFUNDED. The post-payment read-only flight audit now independently verifies the two native character credit receipts and exact full cargo rather than incorrectly rejecting the consumed escrow.

**Evidence:** 8/8 isolated V8 tests of the committed actual four-module Stage A/B/C composition PASS with mocked native SQLite transaction-compatible rows and in-memory disk: prewarp reserve, corporate money debit, full native station proof, pirate+two-player post-raid payment, both actual character balances, duplicate rejection, post-settlement cargo/incident audit and native pirate wreck ID. There are also 5 newly committed standard Node integration scenarios. These have not run in the actual pinned Docker/GameStore worker and do NOT qualify as EVE client gameplay PASS.

**Still blocked:** native root startup injection of real GameStore atomicRows, physical fleet/booking source, authority-backed true native wreck failure proof, persistent world/loss recovery, client wallet display, live Docker and two-client game acceptance. The runtime coordinator is NOT auto-started by simply copying the module into the overlay, and the flags remain OFF.
