## Confirmed defects repaired by this single PR

1. **PI launch false denial.** `coopPiIntegrityGuard.afterLaunch()` previously never passed `sceneEntity` to its own physical-container attestation, so even a legitimate launch would be rejected when the feature is enabled. It now asks the already-native `space/runtime.ensureScene(solarSystemID).getEntityByID(containerID)` for the **actual scene entity** and attests it alongside the native ItemStore item and exact commodity manifest. Missing scene item, wrong owner/quantity or no persisted launch still fail closed. The method never spawns or mints a container.
2. **Expired orphan bypass.** `assertLaunchReady` previously ignored an unresolved launch without `physicalContainerID` after seven days, accepting a new launch despite unproven custody of the original commodities. Unresolved nondeleted native launch receipts now remain blocked until authoritative deletion/reconciliation. Delayed client access or clock changes cannot silently release the fence. **This is conservative**: stale historical receipts may require human recovery before further launches.
3. **Cross-domain original-item double claim.** `coopEconomyConservationAudit` previously checked duplicated market escrow within one source, and NPC cargo versus market, but missed one active native item simultaneously claimed by a **different** domain (contract, manufacturing delivery, market or NPC cargo). The read-only auditor now emits `NATIVE_ITEM_MULTIPLE_ACTIVE_CUSTODIANS` when independent active authorities claim the same original `itemID`. Historical receipts with `active:false` are not treated as current custody. No inventory moves, journal repairs or settlement retries are attempted.
4. **Operator rate documentation + test drift.** Older `COOP_LOCAL_PROGRESSION_V2.md` described 48x as the default, and `tests/coop-local-skill-pacing.test.mjs` still asserted the obsolete `[ValidateSet(6,12,24,48)]` / 48x deployment line. The active deployment script now declares 100x and accepts 48x explicitly. Update that regression to verify the exact current native config while keeping the separate 48x planning calculator. The historical page must not be read as permission to change live training speed. A 100x->48x or 6x->48x switch still requires Chat 33's old-rate settlement/rebase journal, snapshot/backup and observed per-account ETA.
