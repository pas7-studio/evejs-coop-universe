# EveJS native-mechanics → two-player co-op integration audit (2026-10-25)

**Purpose:** source-grounded gap inventory for simultaneous autonomous agents. **Reference snapshot:** upstream `gameboys84/EveJS@c3ea396b6761a0ed3e71ad5b8dd7507f9ae6d69f`; co-op branch `feat/npc-personal-memory-20261024`, draft PR #2 (head at audit start `c9897f1ed2fb539bd38022ad4f3fbe4bb47a3dea`). Never mistake a native service class for verified two-client usability.

**Status vocabulary**
- **NATIVE EXISTS / COOP UNVERIFIED:** executable server functionality is visible, but no specific two-real-client acceptance in this PR. It may work for both players *already* without additional porting; run native client tests before adding adapters.
- **COOP PARTIAL:** overlay/adapter/test exists but full gameplay, persistence or economy chain is not proven.
- **ROUTING / PARITY GAP:** multiple client services implement different subsets, or a stub and a real implementation coexist. Diagnose actual wire calls before editing server.
- **GAMEPLAY INTEGRATION GAP:** independent native systems exist; shared world ownership, inputs/outputs or group credit are not connected.
- **EXPERIMENTAL:** explicitly gated, incomplete, or unverified feature. NOT an end-to-end PASS.

Every link below targets the pinned upstream version. Native EVE RPC functionality is not evidence that a particular client UI displays it correctly.

## 3. High-value vertical slices for agents (nonoverlapping)

### A. Discovery and exploration loop — EXPLORATION agent, P0/P1
1. Start with `scanMgrService`, `probeScanRuntime`, `bookmarkService`, `wormholeMgrService`, dungeon site service.
2. A probes real signature, creates native bookmark; B in native fleet warps there by allowed path. If portal: A and B independently traverse the same native endpoint, enforce ship mass/polarization, reach same destination scene.
3. Salvage/cargo recovered into actual character inventory, not a display-only counter.
4. Negative tests: stale bookmark, wrong system, wormhole collapse between pilots, reconnect, different fleet.
**DoD:** 2 true clients, two separate ships, native signature discovery→shared site→physical cargo or loot. Avoid implementing your own signature generator until stock is demonstrated broken.

### B. Contracts, corp storage, and LP rewards — SOCIAL/ECONOMY agent, P0/P1
1. Trace actual client service RPC routing for `contractProxy` vs `contractMgr` and `LPStoreMgr` vs `LPService` in the service router; **do not assume stubs mean feature unavailable**.
2. A creates real item exchange or courier contract; B accepts and fulfills. Verify escrow/material transfer and both balance updates after crash/reconnect and expiry.
3. Both form/join a single native corp; prove corp hangar deposits/withdrawals and job ownership with role checks.
4. Obtain real LP from agent missions, purchase a stocked native `LPStoreMgr` offer; check each LP, ISK and required-item debit exactly once.
**DoD:** native UI and persistent ownership/ISK/LP at each stage. For auctions, first document unsupported path rather than silently enabling.

### C. Living resource economy — INDUSTRY/AI agent, P0 (depends on stock validation)
1. Native miner ore → real owner-tagged persistent `itemStore` stock depot. Use stable unique delivery receipt; no double create.
2. Real native reprocessing consumes source once; real blueprint job consumes minerals/taxes/ISK once and creates output item.
3. A and B can buy/sell produced units on real market. NPC production only after a real NPC inventory owner/wallet and automated manufacturing order exist.
4. PI, gas/ice and moon extraction are secondary real resource sources and must enter the same inventory authority.
**DoD:** supply balance equation and forced crash tests between each authoritative transfer.

### D. Combat recovery and progression — QUALITY/PROGRESSION agent, P0 quick wins
1. Native repair quote/payment/HP persistence for both pilots after battle.
2. Insure spare hull, destroy during combat, verify one insurance payout, relog and replacement at real market price.
3. Verify actual NPC bounty payment and standing transaction to each eligible pilot (never double grant on group kill).
4. Two accounts train Omega skills at configured 6x, identical rules after relog/offline; confirm client-facing estimates; no premium-only cosmetic fake state.
**DoD:** real item/wallet/HP/SP snapshot before/after. Turn off any unaudited console GM shortcuts for user acceptance.

### E. Faction co-op missions — MISSION agent, current P0 owner
1. Native accepted objective linkage, participant opt-in, genuine witness/contribution, owner and peer journal updates.
2. Rewards one time per eligible character, no shared courier cargo double-consumption, consistent standings and LP.
3. Versioned event receipt after crash/reconnect to avoid a second payout. Only then enable automatic second mission turn-in.
**DoD:** agent RPC and both UI journals/reward history; duplicate completion is idempotent, no credit to AFK unrelated fleet members.

## 4. Research blockers and explicit implementation warnings

**B01 / P0 overlay maintenance (source-tested):** `scripts/patch-evejs-coop.cjs` calls `coop-fleet-mission-native-patch.cjs` twice for `agentMissionRuntime.js` and `dungeonUniverseSiteService.js` (the earlier call also covers `missionRuntimeState.js`). **I ran a read-only test against all THREE pinned upstream files:** first apply changes content, second apply is an exact NO-OP, removal once restores original bytes, removal twice is another NO-OP for all three. Therefore duplicate application is currently **redundant but idempotent on this pinned source**, not by itself an observed runtime failure. Still consolidate duplicate calls with the mission/overlay owner for clarity and run the complete overlay `--dry-run`, no-op reapply, `--remove` and tests in actual Node; do not infer real deployment safety from isolated helper testing.

**B02 / P0 native economy:** NPC hauler virtual depot is not native itemStore station inventory. Claiming "ore delivered", "manufacturing playable" or "dynamic market" needs real owner-tagged persisted items and receipts.

**B03 / P0 mission payouts:** `EVEJS_COOP_FLEET_MISSION_TURNIN: '0'` deliberately disabled in LivingCoop. `EVEJS_COOP_FLEET_MISSION_SHARE` config is present but code still needs verification. No claim of full co-op mission payout.

**B04 / P0 live proof:** 2-client physical game, original pinned Docker build, client UI, native wallet/cargo/state and restart replay remain unverified. Server-side tests alone cannot satisfy "playable co-op".

**B05 / ownership/recovery:** Direct EveJS stock trade transfers wallet then items without a single atomic commit. Contracts, PI launch, refinery, insurance, market escrow and new NPC cargo transactions must be tested for partial settlement and replay. Do not add alternate free item/ISK credit to bypass a failed state transition.

**B06 / version & agent concurrency:** One draft PR and multiple worker agents are operating simultaneously. No merge, CI run, deployment, restarts, market rebuild, Docker volume reset, or modification of local user's game without explicit authorization. One feature family per agent; commit small changes, report exact hash and acceptance evidence; don't overwrite agent files with stale SHAs. Put new findings in docs, not bloated AGENTS.md; log dependency handoffs.

## 5. Required audit/acceptance evidence template

For each row / feature, record **native entrypoint**, client request name and arguments, exact server revision, feature flags, two distinct character/ship IDs (sanitize in shared output), before/after owner+inventory+wallet, expected persisted state after re-login/restart, negative cases, actual 2-client screenshot/log or equivalent approval-limited proof, and **status: SOURCE_CONFIRMED / TEST_PASS / LIVE_PASS / BLOCKED**.

No stage is DONE based only on file existence or one game-master command. No additional speculative roadmap expansion until the first full real gameplay slice is demonstrated.
