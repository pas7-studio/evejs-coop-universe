## Narrow implementation, not an alternative travel service

1. `integration/coopPochvenConduit.cjs` performs a **pure synchronous preflight** of real authenticated character + native active ship itemID, source/destination `worldData` SDE system rows, **reciprocal** original stargate objects found in both system catalogs, source/target region and canonical 27 system names. For non-Pochven native pairs, no Pochven policy is imposed (original gate checks still execute).
2. Only original **Pochven→Pochven** stargates are candidates. Native k-space→Pochven or reverse stargate links are refused (obsolete/disconnected gates cannot become unintended Pochven shortcuts). Nothing changes `jumpSessionToSolarSystem`, `wormholeMgrService`, warp positioning, active ship inventory, ISK, LP, standings or itemStore.
3. For Home **destination**, read original `getCharacterRawStanding(characterID,500026)` at the moment of attempted gate jump. Exact 6.00 passes; 5.99 and absent standing fail. A pilot exiting Home into Internal does not need Home standing. This is **personal RAW** standing, not Social/Diplomacy boost or corporation reputation.
4. Original SDE type registry must identify a ship (category 6) with an explicitly supported subcapital group. Known capital group IDs (Titan, dreadnought, carrier, supercarrier, freighter, jump freighter, capital industrial, force auxiliary) are rejected. Unknown hull group/metadata fail closed until native-specific ship restriction coverage is validated.
5. `scripts/coop-pochven-conduit-patch.cjs` inserts **one** env-gated, default-OFF statement in pinned `space/transitions.js::jumpSessionViaStargate` **before** `beginTransition` so a rejected pilot never starts a jump FX, timer or destination transition. The existing transactional `scripts/patch-evejs-coop.cjs` applies/reverts it while retaining all existing transition hooks. Flag: `EVEJS_COOP_POCHVEN_CONDUIT_GUARD=1` only in an authorized disposable test deployment.
6. The callback cannot spoof `characterID`, faction or gate IDs with client arguments: authoritative state comes from the original server's active ship, live native session, SDE worldData, type registry and persisted character standings.
