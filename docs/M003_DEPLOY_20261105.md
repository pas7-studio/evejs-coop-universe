## 10. Production switched on (same day, 13:0x–14:0x UTC)

The industrial half had never run on the play stack. Four separate things were in the way, and
each was measured before it was changed.

**1. A phase that ran and said nothing.** `EVEJS_COOP_NPC_REFINERY=1` was live for four minutes
with zero refinery events: `coopLoopTick` computed every phase's status and threw it away. The beat
now writes `living-coop-loop-phase {phase,status}` once per change (fork `e4f3416`, `70a1026`), so a
switch that is on and doing nothing is visible instead of indistinguishable from a working one.

**2. The refinery had no budget.** The 2026-11-02 freeze existed because 252 058.47 ISK of refinery
fees could not be accounted for. The wallet it debits is now funded by settled sales with receipts,
the fee is only paid inside a durable `refinery-budget.json` (limit 5 000 000 ISK, `sinceAt` set),
and `EVEJS_COOP_REFINERY_SPEND_LIMIT_ISK=5000000` is an independent second ceiling — the effective
limit is the smaller of the two.

Live: 168 warehouse-tagged stacks refined at 60000682, each with a durable fee receipt and a
commitment row. The corporation's ore became **443 383 429 ISK of minerals at the seeded bids**
(41.7 M Tritanium, 2.6 M Pyerite, plus Scordite/Veldspar and their II/III grades). The fee is ~5 %
of the ore's value and Scordite alone returns ~2.5× its raw bid value as Tritanium + Pyerite, so the
conversion is profitable by construction, not by hope.

**3. The treasury swept the crew to zero.** The native trader pays for a blueprint or a missing
mineral from the PILOT's earned balance; a sweep that zeroes every pilot each beat leaves the
factory unable to buy anything. `EVEJS_COOP_TREASURY_KEEP_ISK` keeps a bounded float per pilot
(default 0 = the old behaviour) and only the excess moves; the rollback path restores the exact
pre-sweep record (fork `3f929b9`, tests `coop-corp-treasury-float`).

**4. The factory had no fixed home.** `factoryStation()` derives home from blueprint receipts, and a
blueprint in transit rewrites its only receipt to `MOVED`, which would send the shopping trip's
cargo back to the seller. `EVEJS_COOP_INDUSTRY_STATION=60000358` pins it.

Production itself is now on with the numbers written next to the flags: manufacture runs 5,
blueprint price cap 500 000 ISK, budget 5 000 000 ISK, shop and input trips on, `LIFT_ANY_TYPE` on.
The arrival allowlist leads with the two products the seeded book really bids for — 672 Caldari
Shuttle (11 245.5 × 10) and 207 Mjolnir Heavy Missile (95.01 × 1 294 484) — and with 215 Iron Charge
S (4.94 × 499 020) and 1816 Inferno Auto-Targeting Light Missile (17.01 × 173 476), the two
ammunition lines the factory can build from its own Tritanium and Pyerite at a profit measured
against the real seeded prices.

Live immediately after the switch: `living-npc-manufacture-attempt` runs every beat and refuses the
one blueprint the corporation owns (`60000358:950:NO_MARGIN` — a Merlin costs ~409 000 ISK of
minerals and bids 97 240), which is the gate working exactly as designed.

## 14. Militia (2026-11-06)

The owner fought for the Caldari State for 141 hours and was thrown out of the militia on
**2026-11-03T19:50Z**. Evidence, in order:

- his war record: `enlistedAt 2026-10-28T23:13:48Z`, `status LEFT`, `leftAt 2026-11-03T19:50:29Z`;
- only ONE code path writes `LEFT`: the `LEAVE_MILITIA` transition;
- the fork commit that stops a mere "Decline"/close of the agent briefing from being read as
  "leave the militia" is `5a6db18`, dated **2026-11-03T22:45Z** - three hours AFTER the flip.

So the leave was the briefing bug, not the owner's action. Restoring it took four fixes, each one
measured before it was written:

1. `mergeWarRecords` merged `wars`/`campaigns` but not `enlistments`, so any war phase that read the
   state before an enlistment changed wrote its stale copy back (`99361bb`). ENLIST/LEAVE now stamp
   `updatedAt` and the merge keeps the newer row per character.
2. The ability window read the character record, not the war store, so after the LEFT row the client
   believed service existed and never offered Enlist while the war layer believed the opposite
   (`99361bb`). `GetMyEnlistment` now answers from the atomic war row, repairs a stale record, and
   `GetCorpAllowedEnlistmentFactions` falls back to `EVEJS_COOP_MILITIA_FACTION_IDS` instead of an
   empty list that made the button dead.
3. A running client shows its own cached copy, so a restored ACTIVE enlistment left the open window
   saying "not in militia" with no rank. The whitelisted admin action `militia_sync` repairs the
   record and pushes the session change inside the server (`4258c8d`).
4. That action first read the row through `readRow` (JSON path `/coop-faction-war/state-v1`) while
   the store writes the flat key `coop-faction-war\u001fstate-v1` - two views of the same row GROUP
   that disagreed, so it tried to re-enlist (denied, already active) and pushed a null faction
   (`fbc1072`). It now reads the flat key the store itself writes.

Final state: war row `ACTIVE`, faction 500001, the original `enlistedAt`, character record
`warFactionID/directFactionID 500001`, effective standing **3.214** (`raw 1.921 + Connections IV`).

Correction to the reasoning recorded in `5814660`: the flat row did survive the container
restarts - the reverts were the merge clobber (1) and, once, this action itself clearing the record
(4). The durable rule is still the same: a row-group member must be written through the store the
war phases use, never beside it.
